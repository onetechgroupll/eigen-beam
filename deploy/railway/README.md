# Railway template walkthrough

[`template.json`](template.json) is the reviewable source for the intended template: one eigen.beam service from `ghcr.io/onetechgroupll/eigen-beam:v0.1`, Railway Postgres, and a private Railway Bucket. The image runs migrations before starting and Railway probes `/readyz` before sending traffic.

Railway currently stores multi-service templates in its dashboard. It does not document a repository JSON format that can import the whole template, so this draft deliberately mirrors the dashboard object rather than pretending to be directly executable.

## Maintainer: publish the live template

1. Confirm that `ghcr.io/onetechgroupll/eigen-beam:v0.1` exists and that the GHCR package is public.
2. In Railway, open **Workspace → Templates → New Template** and create a blank template named `eigen.beam`.
3. Reproduce [`template.json`](template.json) in the template editor:
   - add `eigen-beam` from the Docker image `ghcr.io/onetechgroupll/eigen-beam:v0.1`;
   - enable a public domain on port `3000`, set the healthcheck path to `/readyz`, and leave the image start command unchanged;
   - add Railway's Postgres database resource as `Postgres` rather than a disposable unmounted container;
   - add a Railway Bucket named `eigen-beam-assets`;
   - add every app variable from the snapshot with the same default/reference, required flag and description. In particular, keep `DATABASE_URL=${{Postgres.DATABASE_URL}}` and the five `eigen-beam-assets` references intact.
4. Create the template, deploy it once into a fresh throwaway project, and run the acceptance test below. Fix the dashboard template and snapshot together if they differ.
5. From the workspace Templates page, open the template, add its listing details, and choose **Publish**. An unpublished template is not available to other Railway users.
6. Copy the template URL from the published template. The identifier/code at the end is the `<id>` in the owner-plan button shape `https://railway.app/new/template/<id>`. Railway's current documentation renders the canonical equivalent as `https://railway.com/new/template/<code>` and provides the final button URL in the dashboard; use the copied URL rather than hand-building it.
7. Replace the TODO in the root `README.md`, uncomment the button, and verify the link from a signed-out browser before merging that follow-up.

### Schema and dashboard uncertainties to verify

- Railway does not publish an import schema for dashboard-hosted multi-service templates. The top-level `services`, `buckets`, variable objects and `networking` fields in `template.json` are a review snapshot based on current live template objects, not a guaranteed import contract.
- Add Railway's managed Postgres resource in the editor. The snapshot records its current `postgres-ssl:18` image and variable contract, but Railway may update that implementation independently.
- Railway chooses the Bucket region during deployment and only serializes its name in current template snapshots. Confirm the template exposes `BUCKET`, `ENDPOINT`, `REGION`, `ACCESS_KEY_ID` and `SECRET_ACCESS_KEY` references.
- Current Railway Buckets use virtual-hosted URLs, hence `EB_BUCKET_FORCE_PATH_STYLE=false`. Older buckets can differ; the Bucket **Credentials** tab is authoritative.
- Railway Buckets are private and provide no public base URL. `EB_BUCKET_PUBLIC_URL` is intentionally absent, so eigen.beam serves stored images through its authenticated S3 reader at `/assets/:key`.
- Railway's current public docs use the `railway.com/new/template/<code>` button URL, while the owner-approved plan names the older `railway.app/new/template/<id>` form. Copy the exact published URL Railway supplies and update the commented button accordingly.

## Users: deploy and verify in five minutes

Before starting, have these ready:

- a Resend API key for `EB_RESEND_API_KEY`;
- a sender address for `EB_MAIL_FROM`, such as `eigen.beam <no-reply@example.com>`;
- the sender domain already verified at Resend. Adding an address to `EB_MAIL_FROM` does not verify it, and an unverified domain prevents the first magic link from arriving.

The deploy form asks only for `EB_RESEND_API_KEY` and `EB_MAIL_FROM`. Postgres, the Bucket, their connection variables, `ORIGIN`, the magic-link/cookie signing secret and the MCP bearer token are wired or generated by the template.

After the deploy becomes active:

1. Open `https://<your-domain>/readyz` and require HTTP `200` with `"ok": true`.
2. Open `/account`, enter an inbox you can read, and request a magic link.
3. Confirm that the email actually arrives in that inbox. If it does not, first check the Resend domain verification and that `EB_MAIL_FROM` uses that verified domain.
4. Open the magic link and confirm that the account login completes.

Do not treat a green `/readyz` alone as acceptance: it validates configuration and database readiness, not mail-provider delivery.
